# MAST session resume investigation, 2026-10-27

There is a token-based login path in the public frontend that the initial loaded-bundle review missed.
Repeated real exchanges using the account owner's supplied remembered-login credential successfully renewed the
JWT without another OTP. Automatic renewal is implemented in component 0.5.0. The opaque credential's lifetime
and renewal after the original JWT expires still need observation over time.

## Observed client flow

The login service in the captured main bundle contains:

```javascript
getUserByToken(token) {
  return this.apiSvc.get("api/Users/GetUserByToken", {token})
    // On isSuccess, calls setUserCacheData(response.user).
}
setUserCacheData(user) {
  // For an existing user:
  this.user = user;
  this.userToken = user.token;
}
```

The app startup component in lazy chunk 17 checks `this.userSvc.userToken`, calls
`this.userSvc.getUserByToken(this.userSvc.userToken)`, and on success navigates to the user's active
company's services page. That caller does not request an OTP or a reCAPTCHA token in this code path.

The three credentials have different roles:

| Value | Origin and use |
|---|---|
| `jwtToken` | API JWT, sent in the `jwt: Bearer …` header. The HTTP interceptor replaces it when any response has `new-token`. |
| `user.token` / `userToken` | Returned inside the successful login's user object. Stored separately as `userToken` only when `isApp` is true. Passed to `Users/GetUserByToken`. Its server lifetime is unknown. |
| `token.val` / `loginDto.token` | UUID generated by the client during OTP verification. The separate localStorage `token` wrapper gives it a two-day client expiry. The startup caller uses `userToken`, not this localStorage value. |

The returned `user.token` and the submitted UUID might have the same value; source alone does not establish
their relationship. Use the exact `user.token` returned by the server for the probe.

In web mode (`isApp: false`), `localStorage.userToken` is usually absent, but `localStorage.user` may still
contain the returned `token` field. The `user` getter logs out when `user.expirationDate` has passed, clearing
all four storage keys. Capture the credential while the normal browser login is still valid.

## Runtime checks performed

Initial negative controls were GET requests without JWTs or cookies:

- Omitting the query parameter returned HTTP 404, with the ASP.NET action-selection error that no matching
  Users action was found. The `token` parameter is required for dispatch.
- Supplying the deliberately invalid all-zero UUID returned HTTP 200 with
  `{"user": null, "isSuccess": false, "message": "…"}` and no `new-token` header.

The account owner then supplied a private local credentials file. Two successful exchanges were made without
the old JWT or cookies, using the probe and then the actual integration client:

| Check | Result |
|---|---|
| Resume response | HTTP 200, `isSuccess: true`, `new-token` present |
| JWT expiry (original → first renewal → second renewal, UTC) | `2026-10-29 20:54:54` → `21:47:55` → `21:55:10` |
| Non-timestamp JWT claims | Same keys and values as the original JWT |
| Opaque token returned | Yes; unchanged in both observed exchanges |
| Asset validation | HTTP 200, `isValid: true` |
| Water-card list | HTTP 200; one accessible card |
| `PersonalAreaAsset/GetWaterPeriods` | Successful list response with both the original and renewed JWT |

Initial daily-reading requests returned HTTP 500 with both the original and renewed JWT, including after
session restoration and for 7-day/30-day ranges. After the account owner logged out and completed another OTP
login, the previously captured `user.token` still resumed the session and remained unchanged in the response.
On 2026-10-28, both 7-day and 30-day daily-reading requests then returned HTTP 200 with cumulative readings.
The cause of the earlier HTTP 500 responses is unknown. No personal response values were added to the repository.

Further resume calls advanced the JWT expiry from 2026-10-30 07:50:22 UTC to 12:42:55 and then 14:47:05,
with the opaque token unchanged. These checks establish repeatability over a short interval. The opaque
token's lifetime and post-expiry behavior remain unknown. Periodic renewal before expiry can avoid routine
JWT-expiry logins while MAST continues accepting that credential.

## Repeating the account test

The JWT does not contain the separate `user.token`. While logged in on the real MAST site,
check its presence without exposing the value:

```javascript
Boolean(JSON.parse(localStorage.getItem("user") || "{}").token)
```

If present, copy the minimal credentials into your clipboard using the browser console:

```javascript
copy(JSON.stringify({
  user_token: JSON.parse(localStorage.getItem("user") || "{}").token,
  jwt_token: JSON.parse(localStorage.getItem("jwtToken") || "null")
}, null, 2))
```

Save that JSON in a private local file, for example `/tmp/mast-resume-credentials.json`, with permission
`0600`. Do not paste the clipboard contents into chat or commit the file. Clear the clipboard afterwards.
The optional JWT is only an expiry baseline; the resume request deliberately omits the `jwt` header.

Run from the repository:

```bash
python3 scripts/probe_session_resume.py \
  --credentials-file /tmp/mast-resume-credentials.json \
  --output-file /tmp/mast-resumed-session.json \
  --company-id 110
```

The output file must not already exist. On success the probe saves returned credentials with permission
`0600`, preserving possible rotation. It reports only success flags, timestamps, and a card count. It never
prints tokens, user details, raw responses, request URLs, or exception messages. If a usable JWT is returned
in `new-token`, it checks `ValidateUserAssets` and `GetWaterMeterCards` using that JWT.

The useful result is `resume_success: true`, `jwt_expiry_extended: true`, and successful water access with
the returned JWT. Repeat later using the saved credentials and a new output path to establish repeatability
and token lifetime. A successful exchange after the original JWT expires would establish post-expiry resume.
Changing JWT timestamps locally does not simulate server expiry because it invalidates the signature.

The integration accepts the opaque credential alone during setup or reauthentication and obtains a JWT from it.
It also captures the credential through Reconfigure or userscript version 0.3.0.
New credentials are validated against the configured meter. It renews within 12 hours of JWT expiry,
persists rotated credentials, and falls back to HA reauthentication when a resume credential is rejected and
the JWT is unusable. Network/server errors are retried rather than immediately requesting another OTP.
